SECTION 1: PROJECT OVERVIEW
================================================================================

PROJECT TYPE:
AI-enabled child safety, protection, support, and case-intelligence platform
for India.

PRIMARY GOAL:
Build a unified child-safety ecosystem that combines:
- Online child-safety monitoring
- Cyberbullying and threat detection
- Online grooming-risk detection
- Anonymous child reporting
- Professional human moderation
- Counselling/support
- Emergency SOS
- Parent/adult involvement
- Missing-child identification (CCTV-assisted)
- Cross-case intelligence ("connect the dots")
- Multilingual/regional-language support
- Persistent longitudinal child safety records
- Human-in-the-loop AI
- Privacy-preserving architecture

CORE PRINCIPLE:
AI detects, classifies, summarizes, retrieves, and connects information.
Humans (trained moderators, authorized authorities) verify and make decisions.
The system NEVER independently accuses, contacts law enforcement, or makes
irreversible child-protection decisions.

CORE INNOVATION:
1. Persistent moderator relationship — same moderator stays with a child
2. Longitudinal case intelligence — timeline, not isolated tickets
3. Cross-case "connect the dots" — knowledge graph linking verified cases

SECTION 7: DATABASE ARCHITECTURE
================================================================================

POSTGRESQL (primary relational):
Tables: Users, Children, Adults, Moderators, Cases, Incidents, Reports,
        Evidence, ModeratorNotes, SOSEvents, Notifications, Assignments,
        Escalations, AuditLogs, MissingChildren, ChatMessages

POSTGIS (geospatial, extension on PostgreSQL):
- SOS locations, incident locations, CCTV locations
- Missing-child last-known locations
- Proximity searches, geo-fencing

PGVECTOR (vector search, extension on PostgreSQL):
- Case embeddings, incident similarity
- Semantic search for RAG
- Image/text embeddings for missing child matching

NEO4J (knowledge graph):
Nodes: Child, Incident, Account, Location, Evidence, Time
Relationships: REPORTED_BY, OCCURRED_AT, INVOLVES_ACCOUNT, LINKED_TO
Purpose: Cross-case "connect the dots" capability

REDIS:
- Caching (risk scores, session data)
- Session management
- Job queues
- Real-time events (WebSocket pub/sub)
- Rate limiting

MINIO (S3-compatible object storage):
- Images, videos, screenshots, audio, evidence files

SECTION 8: SECURITY ARCHITECTURE
================================================================================

IDENTITY VAULT:
- Real identity encrypted (AES-256-GCM), stored separately
- Case system uses Protected Child ID (e.g., Child #C8291)
- Identity resolution only by authorized users with logged reason

ACCESS CONTROL:
- RBAC: role-based permissions (child, adult, moderator, authority, admin)
- ABAC: attribute-based (moderator sees only assigned children)

AUTHENTICATION:
- OAuth 2.0, JWT (access + refresh tokens)
- Biometric authentication on Android
- PIN for child session (shared device)

ENCRYPTION:
- TLS for transit
- AES-256-GCM for PII at rest
- Android Keystore for mobile secrets

AUDIT:
- Every sensitive action logged (who, what, when, resource, IP, reason)
- Tamper-resistant (append-only, hashed chain)

FOUR TRUST LEVELS:
1. RAW — original child submission
2. AI-DERIVED — prediction, classification, risk score
3. HUMAN-VERIFIED — moderator-confirmed
4. OFFICIAL — authority-confirmed

SECTION 9: KEY WORKFLOWS
================================================================================

CHILD REPORT WORKFLOW:
Child → anonymous report → privacy layer → case creation → AI analysis →
moderator notification → human review → support/verification/escalation

SOS WORKFLOW:
Child presses SOS → 3s countdown → capture GPS → create emergency event →
notify: linked adults + assigned moderator → emergency response → resolution

MISSING CHILD WORKFLOW:
Report filed → photo + description → AI generates embedding → CCTV uploads →
person detection (YOLO) → embeddings → similarity search → ranked candidates →
human verification

CROSS-CASE INTELLIGENCE:
New verified incident → extract entities → push to Neo4j → pattern detection →
shared accounts/locations/patterns found → flag for moderator/authority review

MODERATOR ASSISTANT (RAG):
Moderator asks question → permission check → case data retrieval from pgvector →
relevant context assembled → LLM generates answer with citations

AI FEEDBACK LOOP:
AI prediction → moderator decision → verified outcome → evaluation dataset →
quality control → aggregated dataset → model training → evaluation → deployment
